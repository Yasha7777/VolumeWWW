# Подготовка обхода перед DUSt3R

Изменение от 2026-11-02. GPU-раннер и приёмник не меняются.

## Поток

`gpu.run_and_save` для обхода загружает исходный `scans/<id>/scan.json`,
вызывает `scan_inputs.prepare`, сохраняет производный файл и только после
успешной загрузки отправляет GPU его путь вместе с соответствующими позами.
Это общий путь первого расчёта и повторного расчёта. Обычная загрузка фото
без обхода работает как раньше.

Производный файл:
`<storage_prefix>/prepared/v1/<analysis_id>/<sha256>.json`.
Исходный файл и строки `colmap_photos` не перезаписываются. `preparation`
содержит версию, хеш исходного JSON, счётчики отбора и диагностику геометрии.
В производный файл попадают только выбранные фото; большие `capture` и
история наблюдений остаются в оригинале. Лимит приёмника — 60 МиБ.

## Что меняется во входе

- Проверяются соответствие кадров, поз, intrinsics, времени и ID обхода.
- Расширенная запись квалифицирует только те точки, связь которых с фото
  уже записана. Новые точки, синтетическая поверхность, исправленные позы
  и усреднённые координаты в фото не добавляются.
- Наблюдение удаляется из производной копии при измеренном разбросе >150 мм,
  если точка имеет ≥8 наблюдений и базу ≥50 мм. В schema 2 учитывается
  максимальная база от первого наблюдения. Порог экспериментальный, не
  гарантия метрической точности.
- Короткая/неизвестная история сохраняет исходную точку как непроверенную.
  Отсутствие или повреждение необязательных dense-данных не удаляет точки.
- Один ID из разных участков/эпох не смешивается. В производном файле ID
  детерминированно перенумерованы маленькими целыми без потери точности JS.
- При потере >25% наблюдений расчёт останавливается с объяснением, вместо
  молчаливого расчёта по облаку с большим провалом покрытия.

## Проверка геометрии

В траектории с интервалом ≤0,2 с смещение >max(0,25 м, 4 м/с × dt)
помечается как подозрительное. Смещение >max(0,5 м, 5 м/с × dt) останавливает
передачу в GPU с закреплёнными позами. Большой промежуток времени сам по себе
не является скачком. Разные `frameEpochs` также не передаются как единое
согласованное облако. Это консервативная проверка, а не доказательство
физической причины скачка; малые и плавные ошибки масштаба она не исправляет.

Приложение продолжает сбор. В schema 2 оно записывает события, участок и
эпоху каждой позы, эпоху фото, отдельные агрегаты точек по `(segment, epoch, id)`
и до шести реальных наблюдений точки со ссылками на траекторию.

Предварительный расчёт `pile.build_cloud` использует ту же проверку. При
несовместимой геометрии облако остаётся доступным, `surface` и оценка дрейфа
не выдаются, на сайте показывается причина. Версия кэша повышена до 5.

## Проверки и выкладка

Бэкенд: `python -m unittest discover -s backend/tests -p test_scan_inputs.py`,
`python -m unittest discover -s backend/tests -p test_gpu_preparation.py`,
`python backend/tests/test_pile.py`.
Фронтенд: `npm run build` из `frontend`.

Подготовка проверена на шести обходах 29–31 октября: пять проходят, исходные
координаты и все фото сохраняются, удаляются 1,8–4,5% наблюдений с большим
разбросом; большой щебень останавливается по скачкам. Производные файлы
прочитаны существующими функциями GPU без запуска реконструкции.

Для применения нужны обычная выкладка сайта/бэкенда и новая сборка приложения
1.05.006 (9). Новая история появится только в новых записях; старые обходы
используют уже имеющиеся dense-данные и проверку траектории. Миграция БД не
нужна. Проверка на физическом iPhone и A/B расчёт неизменным GPU обязательны
перед утверждением, что точность объёма повысилась.
