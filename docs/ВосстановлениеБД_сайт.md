## 1. Что сайт пишет и читает

Фронт в БД **не ходит вообще**: `frontend/src/supabase.js` — anon-клиент
только для auth (`signInWithPassword`, `signUp`, `getSession`,
`refreshSession`, `signOut`, `onAuthStateChange`), ни одного `.from()` в
`frontend/src` нет. Всё остальное идёт через бэкенд под service_role, который
RLS обходит. Отсюда следствие: **политики RLS сайт не защищают** — они начнут
что-то значить только если фронт когда-нибудь пойдёт в PostgREST напрямую.

## 2. Трекаемый SQL и порядок применения

### 2.1. Пять файлов

| # | Файл | Что заводит |
|---|---|---|
| 1 | `supabase/schema.sql` | `profiles` (5 колонок), `analyses` (9 колонок), индексы, RLS, триггер `on_auth_user_created` |
| 2 | `supabase/migration_c2_schema_alignment.sql` | **`colmap_photos` целиком**, `analyses.client_id`, `analyses.glb_url/ply_url`, уникальный индекс `analyses_user_client_uniq` |
| 3 | `supabase/migration_thumbnails.sql` | `analyses.thumbnail_urls`, `colmap_photos.thumb_storage_path/thumb_url` |

| 6 | `supabase/migration_profile_fields.sql` | `profiles.position/city/phone/emails/is_superadmin` (заведён 08.09.2026, см. §7) |

**Порядок обязателен, и он не совпадает с датами файлов.** Ключевое:
`migration_thumbnails.sql:22-24` и `migration_photo_exif.sql:30-31` делают
`ALTER TABLE public.colmap_photos` — а саму таблицу создаёт только C2. Значит:

```
1. schema.sql                          (profiles, analyses, RLS, триггер)
2. migration_c2_schema_alignment.sql   (colmap_photos, client_id, glb_url/ply_url)
3. migration_thumbnails.sql
4. migration_photo_exif.sql
5. migration_client_id.sql             (после C2 — целиком no-op)
6. migration_profile_fields.sql
```

На живой БД (сценарий «докатить») порядок роли не играет: всё под
`IF NOT EXISTS`, повторный прогон безопасен. Порядок критичен для установки
с нуля.

> **Короткий путь: `supabase/INSTALL_site_schema.sql`.** Все шесть файлов,
> собранные в один, в правильном порядке и без `CONCURRENTLY` — вставляется
> в Studio → SQL Editor целиком и выполняется одним Run. Плюс к содержимому
> шести файлов там есть то, чего в них нет: колонки пайплайна на `analyses`
> (§3), бакет `colmap`, `notify pgrst`, проверочные запросы. Синтаксис
> проверен парсером Postgres (libpg_query), на БД не выполнялся.
> Отдельные файлы остаются источником правды по истории изменений — если
> правишь схему, правь и их, и установщик.

### 2.2. Про `migration_c2_schema_alignment.sql` — файл был удалён

Файл убран коммитом `0040a41` («Откат изменений сессии к состоянию начала

Восстановление:

```bash
git show 0040a41^:supabase/migration_c2_schema_alignment.sql \
  > supabase/migration_c2_schema_alignment.sql
```

**Решение: файл возвращён в репозиторий насовсем** (08.09.2026, дословно из
`0040a41^`, без правок). Почему так, а не «схема собирается из внешнего
установщика»:

* Без него репозиторий сайта **не разворачивается в принципе**. Код требует
  `colmap_photos` в шести местах (`analyses.py:419,431,445,460,735,991`,
  `backfill_thumbnails.py:120`), а её `CREATE TABLE` не существует больше
  нигде в этом репозитории.
* Внешний установщик (`Analyz/migrations/INSTALL_from_scratch_2026-09-08.sql:85-99`)
  сам восстановил `colmap_photos` **из этого удалённого файла** — он не
  независимый источник, а его копия. Держать первоисточник в чужом репозитории,
  который может исчезнуть ровно так же, как исчез локальный диск, — это
  повторение той же аварии.
* Установщик — датированный снимок всей схемы Volmetric, включая
  `dust3r_results`, к сайту отношения не имеющий. Сайту нужен свой,
  версионируемый рядом с кодом SQL: правится колонка в `analyses.py` — правится
  файл в соседней папке, одним коммитом.

Цена решения — дубль с `migration_client_id.sql` (пункты A2 и A4 C2 повторяют
её содержимое). Дубль безопасен: обе стороны под `IF NOT EXISTS`. При этом
`migration_client_id.sql` НЕ переписывается — она уже применена на проде, и
её версия индекса (без `CONCURRENTLY`) как раз удобнее, см. ниже.

### 2.3. ⚠️ `CREATE INDEX CONCURRENTLY` в C2 — в транзакции не выполнится

Последний оператор C2:

```sql
CREATE UNIQUE INDEX CONCURRENTLY IF NOT EXISTS analyses_user_client_uniq
  ON public.analyses(user_id, client_id)
  WHERE client_id IS NOT NULL;
```

`CONCURRENTLY` нельзя выполнять внутри транзакционного блока — Postgres
отвечает `ERROR: CREATE INDEX CONCURRENTLY cannot run inside a transaction
block`. **Supabase Studio → SQL Editor оборачивает выполнение в транзакцию**,
поэтому «вставить файл целиком и нажать Run» на этом операторе падает.
`IF NOT EXISTS` не спасает: запрет проверяется раньше, чем существование
индекса `[ВЫВЕДЕНО из поведения Postgres, проверяется одним прогоном]`.

Три рабочих выхода, по убыванию удобства:

1. **Применить `migration_client_id.sql` вместо этого оператора.** Там тот же
   индекс с тем же именем и предикатом, но без `CONCURRENTLY`
   (`migration_client_id.sql:24-26`) — в Studio проходит. На пустой/свежей БД
   блокировка записи, ради которой и нужен `CONCURRENTLY`, не имеет значения.
   После этого оператор A4 в C2 останется единственным непрогнанным — и это
   нормально, индекс уже есть.
2. **Выполнять C2 операторами по отдельности**, последний — отдельным запуском
   вне транзакции.
3. **Через psql на сервере**, где каждый оператор идёт в своём неявном
   транзакционном блоке:
   ```bash
   docker compose exec -T db psql -U postgres -d postgres \
     < supabase/migration_c2_schema_alignment.sql
   ```

И перед созданием индекса на БД с данными — проверить дубли, иначе индекс
просто не создастся (запрос из шапки C2):

```sql
select user_id, client_id, count(*)
from public.analyses
where client_id is not null
group by user_id, client_id
having count(*) > 1;
```

> В закомментированном разделе «ОТКАТ» в конце C2 лежат `DROP TABLE
> colmap_photos` и `DROP COLUMN`. На живой БД это уничтожение замеров.
> Файл целиком в Studio не выделять «чтобы наверняка» — комментарии
> комментариями, но раскомментировать их случайно проще, чем кажется.

## 4. Storage

### 4.1. Что нужно сайту

Ровно один бакет — **`colmap`, публичный**:

```sql
insert into storage.buckets (id, name, public)
values ('colmap', 'colmap', true)
on conflict (id) do nothing;
```

Имя зашито константой `COLMAP_BUCKET = "colmap"` в двух местах:
`analyses.py:33` и `backfill_thumbnails.py:33`. Переменной окружения для него
нет — поменять имя бакета без правки кода нельзя.

Публичность обязательна: бэкенд формирует ссылки через `get_public_url`
(`analyses.py:715,728`, `backfill_thumbnails.py:88`), кладёт их в
`colmap_photos.public_url`/`thumb_url` и в `analyses.photo_urls`/`thumbnail_urls`,
а браузер тянет картинки прямо оттуда — `<img src={u}>` в `History.jsx:892`.
Токенов и подписей в этой цепочке нет. Приватный бакет = битые превью во всей
истории.

Отдельные Storage-политики не нужны: запись идёт под service_role (он RLS
обходит), чтение — публичное.

### 4.2. Схема хранения

На каждый кадр создаётся **два объекта** (`analyses.py:653-728`):

```
{analysis_id}/{uuid}.jpg          ← ОРИГИНАЛ, байт в байт как прислал клиент
{analysis_id}/{uuid}_thumb.jpg    ← 400px JPEG для карточек истории
```

* Первый сегмент пути — `analysis_id`, а не `user_id` (`analyses.py:705`).
  Это важно для §4.4.
* Оригинал не пересохраняется Pillow'ом ни на байт — из него расчётный сервер
  читает EXIF (фокусное расстояние). Уменьшенная копия живёт отдельным
  объектом и оригинал не подменяет.
* Расширение в пути всегда `.jpg`, независимо от исходного файла
  (`analyses.py:705`); настоящий тип уходит в `content-type` при заливке
  (`analyses.py:713`).
* Если миниатюра не сделалась (битый файл), `thumb_url` = ссылка на оригинал
  (`analyses.py:719`), а `thumb_storage_path` остаётся `NULL` — фронт не
  ломается, но при удалении замера убирать в Storage будет нечего.
* Удаление замера подчищает оба пути (`analyses.py:996-1006`), сами строки
  `colmap_photos` уходят каскадом по FK.
* Задним числом миниатюры досоздаёт `backend/scripts/backfill_thumbnails.py`
  (`docker compose exec backend python -m scripts.backfill_thumbnails`).

### 4.3. Бакет `analysis-photos` создавать НЕ надо

## 5. Переменные окружения

Пять граблей, каждая из которых уже стоила времени.

### 5.1. `.env` бэкенда лежит в КОРНЕ `VolumeWWW`, не в `backend/`

`docker-compose.yml:6` — `env_file: .env`, путь относительно файла compose,
то есть корня репозитория. В образе бэкенда `.env` нет вообще:
`backend/Dockerfile` копирует только `requirements.txt`, `app/` и `scripts/`.
Директории `backend/.env` в проекте не существует — положить файл туда значит
не положить его никуда, и контейнер поднимется без переменных.

`Config.env_file = ".env"` в `config.py:17` — это про запуск бэкенда локально,
из папки `backend/`. В докере значения приезжают окружением, не файлом.

> Общая инструкция (`Analyz/ИнструкцияВосстановленияБД.md`, шаг 5) называет
> путь `backend/.env` — **это неточность, ориентируйся на `docker-compose.yml:6`.**
> Там же `frontend/.env` — на самом деле `frontend/.env.local` (§5.3).

Полный список того, что читает бэкенд (`backend/app/config.py:5-14`):

```env
SUPABASE_URL=
SUPABASE_SERVICE_KEY=      # service_role
SUPABASE_JWT_SECRET=       # им auth.py:17 проверяет подпись токенов сайта
N8N_WEBHOOK_URL=           # TEST
N8N_WEBHOOK_URL_PROD=      # PROD
N8N_TIMEOUT=3600           # необязательна, дефолт в config.py:13
```

### 5.2. Оба `N8N_WEBHOOK_URL` обязательны, дефолтов у них нет

`config.py:10-11` объявляет их как `str` без значения по умолчанию. Отсюда два
РАЗНЫХ отказа, и путать их не надо:

* **Переменная отсутствует** → pydantic валится на `settings = Settings()`
  (`config.py:21`), это происходит на импорте — контейнер бэкенда падает на
  старте с `ValidationError`, `/api/health` не отвечает.
* **Переменная есть, но пустая** (`N8N_WEBHOOK_URL=`) → пустая строка проходит
  валидацию `[ВЫВЕДЕНО: `str` принимает `""`]`, бэкенд поднимается, health
  отвечает — а загрузка замера возвращает 500 «Конфигурация n8n URL не найдена»
  (`analyses.py:562-564`), и то же самое делает rerun (`analyses.py:914-916`).
  Симптом со стороны пользователя: сайт работает, история открывается, а любая
  загрузка падает.

`N8N_WEBHOOK_URL_PROD` нужен, даже если PROD-прогонов пока нет: он выбирается
флагом `is_prod` из формы (`analyses.py:562`), и без него сломается ровно
половина кнопок.

### 5.3. Фронт собирается на маке, `dist/` коммитится в git

`frontend/Dockerfile` — это `FROM nginx` + `COPY dist/`. Node внутри нет,
`npm ci` на сервере не выполняется. Vite бакает `VITE_SUPABASE_URL` и
`VITE_SUPABASE_ANON_KEY` **в момент сборки на маке**, из `frontend/.env.local`
(файл в `.gitignore`, как и `.env`). Серверный `.env` на фронт не влияет вообще.

Сборка и выкат — `./git_auto_commit.sh` (собирает, проверяет артефакт,
коммитит, пушит). На сервере остаётся `git pull origin main && docker compose
up --build -d`.

Поменялся проект Supabase или ключи → правь `frontend/.env.local` и
**пересобирай локально**, иначе фронт продолжит ходить в старый Supabase, что
бы ни стояло на сервере.

### 5.4. ‼️ Проверка роли ключа перед сборкой — обязательный шаг

**Что случилось.** В `frontend/.env.local` под именем `VITE_SUPABASE_ANON_KEY`
лежал **service_role**-ключ. Vite вкомпилировал его в бандл, и бандл уехал в
git. Проверено по репозиторию — заражены три коммита:

| Коммит | Дата | Файл в `frontend/dist/assets/` | Роль ключа в бандле |
|---|---|---|---|
| `a9258b4` | 2026-09-05 | `index-BUCcg2uM.js` | `service_role` |
| `814163f` | 2026-09-05 | `index-DB7XhooB.js` | `service_role` |
| `364786c` | 2026-09-06 | `index-BIUWK5bc.js` | `service_role` |

Ключ отозван — **и это ломает вход, пока фронт не пересобран.** Проверено
09.09.2026 обращением к Kong:

| Ключ | `GET /auth/v1/settings` |
|---|---|
| из `frontend/.env.local` (`role=anon`) | `200`, отдаёт конфигурацию |
| из собранного бандла `dist/assets/index-BIUWK5bc.js` (`role=service_role`) | `401 {"message":"Invalid authentication credentials"}` |

Это ровно тот текст, который видит пользователь при регистрации: Kong отзывает
ключ на уровне шлюза, `signUp` до GoTrue не доходит. **Лечится пересборкой
фронта**, схема БД тут ни при чём:

```bash
./git_auto_commit.sh                                  # на маке: сборка + проверка + push
# на сервере: git pull origin main && docker compose up --build -d
```

Текущий `frontend/.env.local` содержит рабочий anon-ключ (проверено там же),
так что правит ситуацию именно пересборка, а не смена ключа. **Но в истории
git старый ключ остался** — он вычищается только переписыванием истории либо остаётся
там навсегда; отзыв ключа делает его безвредным, и это единственное, что уже
сделано.

Почему это была не «мелкая утечка»: фронт в БД не ходит и RLS сайт не защищает
(§1). service_role в браузере = полный доступ ко всем таблицам всех
пользователей мимо любых политик, у кого угодно, кто открыл сайт и посмотрел
в исходники бандла.

**Шаг, который теперь обязателен перед каждой сборкой** — декодировать payload
и убедиться, что там `anon`:

```bash
cd ~/Desktop/ИсследованиеМассы/www/VolumeWWW
python3 - <<'PY'
import base64, json, pathlib
for line in pathlib.Path('frontend/.env.local').read_text().splitlines():
    if line.startswith('VITE_SUPABASE_ANON_KEY='):
        tok = line.split('=', 1)[1].strip().strip('"').strip("'")
        p = tok.split('.')[1]; p += '=' * (-len(p) % 4)
        print('role =', json.loads(base64.urlsafe_b64decode(p)).get('role'))
PY
# должно напечатать: role = anon
```

Та же проверка по УЖЕ собранному бандлу — она поймает и ключ, приехавший из
любого другого места:

```bash
python3 - <<'PY'
import base64, json, pathlib, re
pat = re.compile(r'eyJ[A-Za-z0-9_-]{10,}\.eyJ[A-Za-z0-9_-]{10,}\.[A-Za-z0-9_-]{10,}')
for f in pathlib.Path('frontend/dist').rglob('*.js'):
    for tok in set(pat.findall(f.read_text(errors='ignore'))):
        p = tok.split('.')[1]; p += '=' * (-len(p) % 4)
        try: role = json.loads(base64.urlsafe_b64decode(p)).get('role')
        except Exception: continue
        print(f, '→', role)
PY
# допустимо только role = anon; service_role → НЕ КОММИТИТЬ, отозвать ключ
```

Существующая защита в `git_auto_commit.sh:23` ловит **только** dev-заглушки
(`localhost:54321`, `local-anon-placeholder`) — роль ключа она не смотрит,
поэтому service_role проходил мимо неё беспрепятственно. Проверку выше стоит
внести в скрипт; пока этого не сделано, она выполняется руками.

### 5.5. Имена переменных в `/opt/supabase/.env` — НЕстандартные

На сервере установка Supabase сделана не по официальному docker-compose, и
переменные названы иначе, чем в документации Supabase:

Установка — стековая (`STACK_VERSION`, `INSTALL_DIR=/opt/supabase`), имена
сверены с файлом 09.09.2026:

| В `/opt/supabase/.env` | Официальное имя | Куда идёт |
|---|---|---|
| `SERVICE_SUPABASESERVICE_KEY` | `SERVICE_ROLE_KEY` | `SUPABASE_SERVICE_KEY` бэкенда, n8n, приёмник |
| `SERVICE_SUPABASEANON_KEY` | `ANON_KEY` | `VITE_SUPABASE_ANON_KEY` фронта |
| `SERVICE_PASSWORD_JWT` | `JWT_SECRET` | `SUPABASE_JWT_SECRET` бэкенда (`auth.py:17`) |
| `SERVICE_PASSWORD_POSTGRES` | `POSTGRES_PASSWORD` | доступ к БД через psql |
| `ENABLE_EMAIL_AUTOCONFIRM` | `GOTRUE_MAILER_AUTOCONFIRM` | подтверждение почты, см. §6 шаг 1а |
| `EXTERNAL_HOST` / `API_EXTERNAL_URL` | — | `https://supabase.gottland.ru` |

**Копировать примеры из официальной документации Supabase нельзя** — там
`grep -E 'SERVICE_ROLE_KEY|ANON_KEY|JWT_SECRET' .env` не найдёт ничего, и
переменные молча получат пустые значения. Смотреть надо так:

```bash
# на сервере, где поднят supabase.gottland.ru
grep -E 'SERVICE_SUPABASE|SERVICE_PASSWORD' /opt/supabase/.env
```

Сверка «локальное = серверное» (09.09.2026, сравнивались значения, в документ
не выносятся):

* `.env` → `SUPABASE_SERVICE_KEY` == `SERVICE_SUPABASESERVICE_KEY` ✔
* `.env` → `SUPABASE_JWT_SECRET` == `SERVICE_PASSWORD_JWT` ✔
* `frontend/.env.local` → `VITE_SUPABASE_ANON_KEY` == `SERVICE_SUPABASEANON_KEY` ✔
* оба серверных ключа проверены на подпись этим `SERVICE_PASSWORD_JWT` — сходятся.

То есть **бэкенд настроен верно, и правильный anon-ключ на маке лежит** — вся
проблема в §5.4 только в том, что фронт с ним не пересобран.

> Ключи и JWT-секрет в трекаемых файлах не хранятся: `.env` и `.env.*` в
> `.gitignore`. Если значения попали в переписку/тикет — считай их
> скомпрометированными и перевыпускай (смена `SERVICE_PASSWORD_JWT` разлогинит
> все живые сессии и потребует правки ключа в 22 узлах n8n).

### Шаг 1а. ‼️ Подтверждение почты — вход может быть невозможен

**ПРОВЕРЕНО НА ЖИВОМ СЕРВЕРЕ 09.09.2026** — доступ на сервер для этого не нужен,
GoTrue отдаёт свою конфигурацию по anon-ключу:

```bash
K=$(grep '^VITE_SUPABASE_ANON_KEY=' frontend/.env.local | cut -d= -f2-)
curl -s -H "apikey: $K" https://supabase.gottland.ru/auth/v1/settings
```

Ответ (значимая часть):

```json
{"disable_signup": false, "mailer_autoconfirm": false, "phone_autoconfirm": true, "sms_provider": ""}
```

То есть: регистрация разрешена, **автоподтверждение почты выключено**.
Подтверждать письмом — единственный путь, а письма слать нечем, если `SMTP_*`
пусты. Что стоит в самих переменных — смотреть на сервере:

```bash
grep -Ei 'autoconfirm|mailer|^SMTP' /opt/supabase/.env
docker compose exec auth env | grep -E 'GOTRUE_(MAILER|SMTP|EXTERNAL_EMAIL)'
```

Сверено с файлом 09.09.2026 — картина ровно та, что видна снаружи:

```env
DISABLE_SIGNUP=false
ENABLE_EMAIL_SIGNUP=true
ENABLE_EMAIL_AUTOCONFIRM=false     # ← вот он
ENABLE_PHONE_AUTOCONFIRM=true      # к сайту отношения не имеет: вход по email
SMTP_ADMIN_EMAIL=                  # пусто
SMTP_HOST=                         # пусто
SMTP_PORT=587
SMTP_USER=                         # пусто
SMTP_PASS=                         # пусто
SMTP_SENDER_NAME=                  # пусто
```

Что при этом делает **код сайта** (это прочитано, а не предположено):

* `Register.jsx:52` → `AuthContext.jsx:142-143` → `supabase.auth.signUp(...)`,
  без `emailRedirectTo`. При успехе — экран «Проверьте почту» (`Register.jsx:58,63-73`)
  и редирект на `/login` через 3 с (`Register.jsx:59`);
* `Login.jsx:17` → `signInWithPassword` (`AuthContext.jsx:139-140`). Ошибка
  показывается пользователю как есть — переведена только
  `Invalid login credentials` (`Login.jsx:20-22`), всё остальное выводится
  по-английски.

Что делает GoTrue при `mailer_autoconfirm: false` (значение подтверждено выше;
дальнейшее поведение — `[ВНЕШНЕЕ, не из этого репозитория]`): учётка
создаётся неподтверждённой и
`signInWithPassword` отвечает `400 Email not confirmed`; при пустом SMTP письмо
отправить нечем, поэтому либо сам `signUp` вернёт ошибку отправки, либо письмо
просто не придёт. **В обоих исходах пользователь войти не сможет**: на экране
входа он увидит английское `Email not confirmed`, а в интерфейсе регистрации —
обещание письма, которого не будет.

Три выхода:

1. **Включить автоподтверждение** (быстро, годится для восстановления):
   ```bash
   cd /opt/supabase
   sed -i 's/^ENABLE_EMAIL_AUTOCONFIRM=false/ENABLE_EMAIL_AUTOCONFIRM=true/' .env
   docker compose up -d auth
   # проверка снаружи: должно стать "mailer_autoconfirm": true
   curl -s -H "apikey: <anon>" https://supabase.gottland.ru/auth/v1/settings
   ```
   Побочный эффект: экран «Проверьте почту»
   (`Register.jsx:63-73`) станет враньём — письма не будет, а войти можно
   сразу. Косметика, но пользователей это путает.
2. **Настроить SMTP** (правильный вариант для боевой эксплуатации): заполнить
   `SMTP_*` и отправителя, перезапустить `auth`. Тогда текущий текст экрана
   регистрации становится правдой и менять во фронте ничего не нужно.
3. **Подтвердить конкретного пользователя руками** — когда нужно просто
   пройти смоук-тест:
   ```sql
   update auth.users set email_confirmed_at = now()
   where email = '<email>' and email_confirmed_at is null;
   ```
   `[ВЫВЕДЕНО: колонка auth.users.email_confirmed_at — стандартная схема
   GoTrue, а не код этого репозитория; проверить select'ом из шага 1]`

## 7. Что проверить на живой БД

Всё в этом разделе — вопросы, ответ на которые из кода не получить.

### 7.1. `analyses.title` или `analyses.name`?

**Настоящая колонка — `title`.** Со стороны сайта разночтения нет:

* `schema.sql:19` — `title TEXT NOT NULL DEFAULT 'Без названия'`;
* бэкенд пишет `title` (`analyses.py:631`) и читает `title`
  (`analyses.py:818,920,960`);
* фронт читает `title` (`History.jsx:245,250,580,849`).

Строки `name` в контексте `analyses` в репозитории сайта нет ни одной —
`name` встречается только как колонка `profiles` (`profile.py:40`,
`analyses.py:768,846,877`).

Значит, `select a.name` в `Analyz/migrations/CHECK_runs.sql` (запросы ③ и ④) —
**ошибка в самом проверочном запросе**, а не признак того, что в БД другая
колонка. Проверить одним запросом:

```sql
select column_name from information_schema.columns
where table_schema = 'public' and table_name = 'analyses'
  and column_name in ('title', 'name');
-- ожидается ровно одна строка: title
```

Если так и есть — чинить надо `CHECK_runs.sql` (`a.name` → `a.title`) в
соседнем репозитории. Правка там за рамками этой инструкции, но без неё
запросы ③/④ будут падать с `column a.name does not exist`.

### 7.2. `profiles`: пять колонок мимо трекаемого SQL — исправлено

`position`, `city`, `phone`, `emails`, `is_superadmin` код читает и пишет
(§1.3), а `schema.sql:7-13` их не заводит. Заведён новый файл
**`supabase/migration_profile_fields.sql`** — `ADD COLUMN IF NOT EXISTS`, на
проде no-op, для чистой установки обязателен.

Типы выводились из кода, но **09.09.2026 сверены с живой БД и совпали**:
`position/city/phone` — `text`, `emails` — `ARRAY` (`text[]`),
`is_superadmin` — `boolean`. Единственное расхождение с
`migration_profile_fields.sql`: на проде у `emails` и `is_superadmin`
**нет дефолтов** (`'{}'` и `false` соответственно). Коду это безразлично —
он пишет `data.emails or []` (`profile.py:45`) и читает
`bool(...get("is_superadmin"))` (`analyses.py:251`), то есть NULL для него
эквивалентен пустому массиву и `false`. Чистая установка из нашего файла
получит дефолты — это строже прода, но не расходится с ним по поведению.

Перепроверить, если схему трогали:

```sql
select column_name, data_type, is_nullable, column_default
from information_schema.columns
where table_schema = 'public' and table_name = 'profiles'
order by ordinal_position;
-- ожидается 10 колонок: id, name, company, created_at, updated_at,
-- position, city, phone, emails, is_superadmin
```

### 7.3. Полная сверка колонок сайта

```sql
select table_name, column_name, data_type, is_nullable
```

`on_auth_user_created` на `auth.users` на месте. Бакеты `colmap` и

### 7.4. PostgREST видит таблицы

Схему он кэширует: свежесозданная таблица может отдавать 404, пока кэш не
сброшен.

```bash
K='<service_role>'
for t in profiles analyses colmap_photos; do
  printf '%-16s ' "$t"
  curl -s -o /dev/null -w '%{http_code}\n' -H "apikey: $K" \
    -H "Authorization: Bearer $K" \
    "https://supabase.gottland.ru/rest/v1/$t?select=*&limit=1"
done
```

404 при существующей таблице → `notify pgrst, 'reload schema';` в SQL Editor
либо перезапуск контейнера `rest`.

### 7.5. Мелочи, которые всплывут позже

* **`is_nullable`, дефолты, реальные индексы** восстановить из кода нельзя в
  принципе — только запросом 7.3 к живой БД.
* **RLS на `colmap_photos`** в трекаемом SQL нет, и что стоит в проде —
  неизвестно. Сайту это безразлично (бэкенд под service_role), но при
  включении RLS без политик к таблице перестанет ходить всё, что работает не
  под service_role.
* **Фоновые задачи умирают вместе с процессом uvicorn** — это не про схему, но
  выглядит как «БД не работает»: замер навсегда останется в `pending`, если
  бэкенд перезапустили в момент прогона. Лечится кнопкой rerun
  (`analyses.py:900-973`), она умеет перезапускать и `pending`.
* **Обрыв связи после создания строки, но до заливки фото** оставит `analyses`
  с пустым `photo_urls`; ретрай очереди попадёт в идемпотентность по
  `client_id` (`analyses.py:601-612`) и получит ту же пустую строку. Замер
  зависнет в `pending` навсегда — при разборе «после восстановления не
  работает» проверять это в первую очередь:
  ```sql
  select id, created_at from public.analyses
  where status = 'pending' and coalesce(array_length(photo_urls,1), 0) = 0
  order by created_at desc;
  ```
